# for document

适用于给人读的文字：报告、方案、说明、手册、会议纪要，以及给开发者看的代码注释、提交说明、日志、PR 描述、RFC 和技术博客。读者读这些文字，是为了理解内容、评审变更、决定方案或照着操作。

通用规则（[`for-all.md`](for-all.md)）同样适用。

### D1 主语写名称，不写“我们”“你们”

主语必须写名称：公司名、品牌名、人名或职务。不得写“我们”“你们”“他”“她”“它”。表头和分工表同样适用。主语是作者本人或作者所在的团队时，可以省略主语，比如周报里写“本周上线了导出功能”。

原因：文档会被转发，读的人不一定知道“我们”指谁。

- ✗ 表头：“我们负责”“你们负责”
- ✓ 表头：“供应商负责”“客户负责”

### D2 先写结论，再写依据

必须先写结论，再写依据。每一节的第一句宜写这一节的结论。

- ✗ 本季度共收到 120 条反馈。其中 45 条与加载速度有关……综合来看，加载速度问题要优先处理。
- ✓ 本季度优先处理加载速度问题。依据：120 条反馈里有 45 条与加载速度有关，占 38%。

### D3 一段只讲一个主题

一段必须只讲一个主题，一段宜不超过 6 句。

### D4 三项以上用列表

三项以上的并列内容、三步以上的操作，必须写成列表。操作步骤用编号列表。

### D5 操作步骤一步一个动作，说明与步骤分开

操作步骤必须一步写一个动作，每一步以动词开头。说明和提醒必须与步骤分开写，说明里不得夹带要求。

- ✗ 打开设置并点击账号，修改邮箱，注意新邮箱要能收信。
- ✓
  1. 打开“设置”。
  2. 点击“账号”。
  3. 修改邮箱地址。
  4. 打开新邮箱里的验证邮件，点击验证链接。

  说明：验证完成前，登录仍使用原邮箱。

### D6 风险提示先写动作或条件，再写后果

风险提示必须先写要做的动作或触发的条件，再写不照做的后果。

- ✗ 请注意数据安全。
- ✓ 删除前先导出数据。删除后，数据不能恢复。

### D7 提醒分三级：警告、注意、说明

需要提醒读者的内容，必须按风险大小用三个固定的词开头：

| 词 | 用在什么时候 |
|---|---|
| 警告 | 继续操作可能造成数据丢失、安全问题或无法撤销的结果 |
| 注意 | 继续操作可能失败，或结果不符合预期 |
| 说明 | 补充背景、定义或依据 |

- ✗ 温馨提示：删除后无法恢复哦。
- ✓ 警告：删除后，数据不能恢复。

### D8 代码注释写原因，提交说明先写改了什么

代码注释必须写为什么这样做，不得复述代码在做什么。提交说明的第一行必须写改了什么，正文写为什么改。

- ✗ `// 遍历列表`
- ✓ `// 跳过已删除的记录：接口返回的数据里仍包含已删除的记录`
- ✗ 提交说明：“修改了一些问题”
- ✓ 提交说明：“修复导出表格时日期少一天的问题”，正文写原因：时区按 UTC 计算。

### D9 技术文稿按用途保留信息

PR、RFC 和技术博客必须按 D10—D12 中对应的规则写。与通用规则或 D1—D8 不一致时，以对应文稿的规则为准。用户指定格式或仓库已有模板时，必须遵循，并按文稿用途补足信息。

- 正文必须让未参与此前对话的目标读者读懂。内部编号、聊天结论或本机路径不能代替问题说明和读者可访问的依据。
- 必须保留影响理解和判断的触发条件、适用范围、设计理由、证据和限制。不得以 G20 为由删去必要论证。
- 性能、正确性和兼容性主张必须有对应依据。实验结论必须写清影响结论的环境、条件和测量口径，并给出可核对的结果或来源。
- 篇幅和章节必须随任务复杂度调整。已有内容充分时，不必增加固定章节；不得为填模板编造风险、备选方案或验证结果。
- 正文不得套用 C10 的聊天回执。向用户汇报文稿修改结果时，才按 C10 处理。

### D10 PR 描述服务于代码评审

- 标题和开头必须说明具体问题或新增能力，以及修改后的行为。存在故障时，必须说明触发条件和修改前后的差别。
- 正文宜说明 diff 难以直接表达的机制和设计理由。实现取舍影响评审判断时，必须保留；不必按文件逐项复述修改。
- 验证必须写实际覆盖的行为和结果。影响结论的未验证范围必须明确，不得只写“测试通过”，也不得把新增测试写成已运行测试。
- 涉及接口、数据格式、配置或部署方式变化时，必须说明使用影响；需要迁移或回滚时，必须说明方法或限制。
- 描述必须以最终差异为准。小修复可用一段问题与改动说明，加一段验证结果；不必写成设计文档。

### D11 RFC 服务于方案讨论和决策

- 开头必须写清待解决的问题、提议和文稿状态。尚未决定的方案必须保留提议语气，不得因 D2 而写成已采纳结论。
- 正文必须说明目标、约束和成功判据。容易被误解为本次范围的事项，必须写清边界；不必罗列读者不会预期的非目标。
- 提案必须说明机制和关键取舍。存在可行替代方案时，必须使用相同标准比较收益、成本和风险；保持现状可作为比较基线，不得虚构替代方案来衬托提案。
- 事实、假设、预期收益和验证结果必须区分。关键假设尚未验证时，必须说明验证办法，不得提前声称收益已实现。
- 影响采纳的兼容性、迁移、运行风险和实施依赖必须说明。验证计划必须与已完成验证分开；实施细节展开到足以判断可行性即可。
- 尚待决定的问题必须明确列出，并说明需要什么证据或决策。已确定的取舍必须保留理由，不得以“简洁”为由隐藏分歧。

### D12 技术博客服务于理解和复现

- 开头宜交代要解释的问题和阅读收益，可从具体案例或现象切入。不必每节先写结论；整体顺序必须帮助目标读者理解机制。
- 解释所需的背景、推导、中间步骤、示例和反例必须保留。不得把文章压成变更清单，也不得把有解释作用的重复一律视为冗余。
- 调试或探索过程能解释结论来源时，可按过程展开；必须交代每一步的观察和判断，不宜堆放命令或失败记录。
- 示例、类比和简化模型必须与真实机制区分。简化会影响读者判断时，必须说明适用边界。
- 承诺可复现的教程或实验必须说明前置条件、关键版本、操作和预期结果。概念性代码必须标明省略内容，不得宣称已经运行。
- 原创判断、外部结论和实测结果必须区分。引用外部结论时，必须给出来源，不得把单次实验推广为普遍规律。
- 作者确实参与的实践可用“我”或指代明确的“我们”；教学讲解可用“你”。此处不受 D1 的人称限制，但不得虚构经历或团队身份。
